# Skyward manet：启动提速、启动动画、自动解密

## 一、「解密页等很久」的真正原因

用户反馈「正在读取锁屏方式」要等三十多秒。实机日志逐段拆开后：

| 阶段 | 时间 | 说明 |
|---|---|---|
| 内核启动 → Skyward 首帧 | 7.48 s | bootloader + kernel，改不了 |
| 挂载 super + 模块 | 7.60 → 8.16 s | 0.56 s |
| `publish_descriptions` | 8.16 → 11.22 s | **3.06 s**（重启 servicemanager + 等 init 服务重注册） |
| 9 个 service 启动 | 11.28 → 11.93 s | **0.65 s**（qseecomd 101ms、gatekeeper 102ms、weaver 305ms…） |
| **自检 `sleep 25`** | 11.93 → 37.20 s | **25.29 s** |
| `Job::Open`（读锁屏类型） | 37.22 → 37.68 s | **0.46 s** |

**「读取锁屏类型」本身只要 0.46 秒**，等待全在 `wait_prepared()`。而 prepare 被我自己加的自检脚本挡住 25 秒。

**根因**：`services::start()` 对 `oneshot = true` 的服务是**同步 `.status()` 等它退出**，自检脚本里的 `sleep 25` 就把整条 prepare 拖住了。

**修法**：自检改成后台执行（`(sleep 25; …) &`），prepare 从 37.6 s 降到约 12 s。

## 二、解密实际走哪条路（决定性实测）

在 `data.rs` 的 `open_user_files` 成功分支加 `note_opened()`，把结果写
`/mnt/vendor/persist/skyward/decrypt.txt`（persist 分区，重启后仍可读）：

```
user 0: opened 6e3803381a57a201 (secdiscardable)
```

**结论：走的是 secdiscardable blob（keymint + gatekeeper），NXP eSE 的 weaver 一次都没用到。**

依据：`protectors()` 返回用户全部 blob，`protectors.sort_by_key(|p| matches!(p.bound, Bound::Weaver(_)))` 把 weaver 排最后，所以 secdis 先试，成功即返回。

manet 的两个 blob：

```
6e3803381a57a200.spblob + .pwd + .weaver      ← Android 记录的当前锁屏
6e3803381a57a201.spblob + .pwd + .secdis     ← 姐妹 blob
```

**于是精简掉整条 weaver 链**：

```toml
# 之前
load = ["goodix_core", "xiaomi_touch", "stm_nfc_i2c", "nxp-nci"]
9 个 service（含 weaver / NXP eSE）

# 现在
load = ["goodix_core", "xiaomi_touch"]
8 个 service
```

**注意**：weaver 与 NFC 模块必须**一起删**——只删模块不删服务，`ready_service` 会等 20 秒超时然后 `bail!`，整条 prepare 中断。

## 三、启动动画

`crates/skyward-ui/src/progress.rs`（新，57 行）：

```rust
pub const BEGIN/PARTITIONS/DRIVERS/DESCRIPTIONS/SERVICES/READY = 0..=5;
pub fn stage() -> u8;         // 原子读
pub fn reached(stage: u8);    // prepare 各阶段打点
pub fn phase_ms() -> u64;     // 真实时间驱动动画
pub fn done() -> f32;         // stage/5
pub fn waiting(stage) -> [&str; 3];  // 三语文案
```

`main.rs` 打点：挂载前 → PARTITIONS；加载模块前 → DRIVERS；之后 → DESCRIPTIONS；启服务前 → SERVICES；结束 → READY。

`ui.rs` 主循环：`stage() < READY` 时把 poll 超时压到 **33ms（30fps）**，就绪后恢复 1000ms。

`pages.rs::data_status` 绘制：

- 以图标为圆心、半径 40dp 的**转动环**（1.5 秒一圈，角度由 `phase_ms()` 算，不按帧计数）
- 4 段拖尾，`color::mix(bg, accent, a*0.55)` 渐隐
- 下方 200×4dp **进度条**，按 `done()` 增长，末端 3.5dp 光点
- 文案随阶段变化：正在挂载分区 → 加载驱动 → 登记系统服务 → 启动系统服务 → 读取锁屏方式

## 四、自动解密（移植自 mariusarva/skyward-pudding）

**新文件 `crates/skyward/src/remember.rs`（62 行）**：

```rust
pub const FILE: &str = "/metadata/skyward/credential";
```

- 存锁屏凭据原文，`0600` 仅 root
- `/metadata` 平时只读，写入前 `remount_writable(true)`，写完立刻改回
- 选 `/metadata` 而非 persist：**恢复出厂会格式化它**，凭据自动消失

**流程**：

```
下次进 recovery → 读凭据 → Opened(Ok) 后若主用户还锁着 → 自动 Unlock
  → kmsg: "opening user 0's files with the screen lock kept from before"
  → 成功直接进主页
```

**三重保护**：

| 情况 | 行为 |
|---|---|
| 记住的密码解不开 | 立刻删除并把开关关掉（避免反复试错被 eSE 累计计数） |
| 用户关掉开关 | 立刻删文件 |
| 用户改过锁屏密码 | 旧凭据自动失效 → 失败 → 自动忘记 |

**时序坑（pudding 原版没有处理）**：UI 首帧时 `/metadata` 尚未挂载，启动时 `remember::read()` 会读空。所以真正使用前**再读一次**：

```rust
if remembered.is_none() {
    remembered = remember::read();
    if remembered.is_some() { app.state.remember = true; }
}
```

**UI**：解密页键盘上方一行 `○/● 记住密码，下次自动解密`（`Action::Remember` → `Effect::Remember(bool)`）。

## 五、踩过的坑

1. **`oneshot` 服务是阻塞的** —— `command().status()` 等进程退出，脚本里的 `sleep` 直接拖住整个 prepare。
2. **weaver 服务与 NFC 模块必须成对增删** —— 只删一半会让 `ready()` 超时后 `bail!`，整条链断。
3. **`/metadata` 在 UI 首帧时未挂载** —— 持久凭据要延迟读。
4. **`data.rs` 里 `eprintln!` 在 recovery 中会被丢弃** —— `skyward-crypto` 不依赖 `skyward-sys`，没有 kmsg 通道；要留证就写 persist 分区文件。
5. **`Bound` 不是 `Copy`** —— `match protector.bound` 会移动，必须 `match &protector.bound`。
6. **clippy `write_with_newline`** —— `write!(… "\n")` 要写成 `writeln!`。
7. **debug 分支的 artifact 不带 release** —— `Publish` 只对 main/tag 生效，debug 只能从 Actions 页面下 artifact。
